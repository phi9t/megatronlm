# Learning Tracker: Megatron-LM Hacker Files

## Session Goal
Deep understanding of the three hacker files: `HACKERS_GUIDE.md`, `hack.py`, `hacker_megatron_lm.py`

---

## Concept Checklist

### 1. The Two-Layer Architecture (MCore vs Training Scripts)
- [ ] What problem does this separation solve?
- [ ] What lives in `megatron/core` vs `megatron/training`?
- [ ] How do you decide where to make a change?
- [ ] Why is this boundary important for the hacker scripts?

### 2. The Module Spec System
- [ ] What problem does ModuleSpec solve?
- [ ] How does `build_module()` work?
- [ ] What are the three available layer specs and when to use each?
- [ ] How does `hack.py` bypass the spec system vs how `hacker_megatron_lm.py` uses it?

### 3. TransformerConfig
- [ ] Why does everything flow through TransformerConfig?
- [ ] What are the critical fields?
- [ ] How does `use_cpu_initialization` help hackers?

### 4. Parallelism Architecture (TP, PP, DP)
- [ ] What does each parallelism type split?
- [ ] How do they compose (e.g., TP=2, PP=4, DP=2 on 16 GPUs)?
- [ ] What are ColumnParallelLinear and RowParallelLinear?
- [ ] What are pre_process and post_process in PP?

### 5. Distributed Initialization
- [ ] How does `initialize_distributed()` detect single vs multi-GPU mode?
- [ ] Why must `initialize_model_parallel(1,1)` be called even in single-GPU mode?
- [ ] Why does it call `destroy_model_parallel()` first?

### 6. The Demo Progression
- [ ] Why are the demos ordered config → attention → mlp → layer → model → training → TP → PP → DDP?
- [ ] What does each demo teach?

### 7. The Hacker Script Design
- [ ] How does `hacker_megatron_lm.py` differ from `hack.py`?
- [ ] What are the utility functions and why do they exist?
- [ ] How does interactive mode work?

### 8. Broader Context
- [ ] Why does this onboarding toolkit matter?
- [ ] What would you do if you wanted to add a new attention variant?
- [ ] What would you do if you wanted to add a new model type?
